# PTAF PRO API Client

Клиентская утилита для работы с API PTAF PRO 4.x (в т.ч. 4.3.0). Позволяет управлять правилами, шаблонами политик, настройками трафика, действиями в правилах, конфигурациями тенантов и копировать объекты между тенантами.

---

## ⚠ Предупреждение
**Администрирования происходит с внешнего хоста, не преполагается установка непосредственно на PTAF**

## ⚠ Предупреждение
**Использование утилиты может приводить к ошибкам в работе и переводить инсталляцию PTAF в неработоспособное состояние.**

- Операции изменяют конфигурацию напрямую через API (правила, шаблоны, приложения, списки и т.д.).
- При сбоях сети, несовместимости версий API или ошибках в данных возможны частичные применения изменений, дубликаты или потеря настроек.
- Рекомендуется делать резервные копии конфигурации (снапшоты) до массовых операций и тестировать изменения в тестовой среде.

---

## Функционал

### Главное меню

1. **Работа с правилами** — импорт/экспорт пользовательских правил (в т.ч. с сохранением связей с действиями и состоянием включено/выключено), удаление всех пользовательских правил.
2. **Управление шаблонами и политиками безопасности** — просмотр наборов правил и шаблонов, создание шаблонов, экспорт/импорт шаблона в JSON, копирование шаблона в другой тенант, создание шаблона на основе политики.
3. **Управление настройками traffic_settings** — настройки NGINX (лимит загрузки, access.log, error.log), Envoy (sticky session, TLS), лимиты приложений, debug-режим. Форматы access.log задаются в `config/nginx_access_log_formats.yaml`.
4. **Управление действиями в правилах** — массовая замена, добавление и удаление действий в шаблонах политик и политиках веб-приложений, в т.ч. экспериментальные операции «любое действие» с фильтром по уровню критичности (`threat`). Подробнее см. раздел [Управление действиями в правилах](#управление-действиями-в-правилах).
5. **Получение конфигураций тенантов** — снапшот текущего или выбранного тенанта, снапшоты со всех доступных тенантов (GET config/snapshot).
6. **Восстановление конфигураций тенантов** — восстановление конфигурации безопасности из выбранного файла снапшота (с подтверждением).
7. **Копирование объектов между тенантами**:
   - Копирование защищаемых серверов (бекендов) в другой тенант
   - Копирование ролей в другой тенант
   - Копирование пользовательских действий в другой тенант
   - **Копирование веб-приложения в другой тенант (экспериментальное)** — данные приложения и переназначения правил всегда берутся из снапшота исходного тенанта (GET config/snapshot); копируются приложение, шаблон политики (при отсутствии в целевом тенанте), оверрайды системных и пользовательских правил по именам; опционально сравнение снапшотов после переноса.
8. **Работа с тенантами** — выбор и переключение тенанта, просмотр списка тенантов.
9. **Управление глобальных списков** — работа с глобальными списками (доступно при PTAF 4.2.2+).
10. **Выход**

Часть пунктов меню отображается в зависимости от версии PTAF (например, глобальные списки — с 4.2.2).

## Установка

Требования: Python 3.8+ и `pip`.

1. Клонируйте репозиторий:

```bash
git clone <repository-url>
cd ptaf-pro-api-tools
```

2. Рекомендуется создать виртуальное окружение:

```bash
# Linux / macOS
python3 -m venv venv
source venv/bin/activate

# Windows (PowerShell)
python -m venv venv
.\venv\Scripts\Activate.ps1
```

3. Установите зависимости из `requirements.txt`:

```bash
pip install -r requirements.txt
```

Сейчас в зависимостях: `requests` (HTTP-запросы к API PTAF), `PyYAML` (форматы access.log).

## Управление действиями в правилах

Пункт главного меню **«4. Управление действиями в правилах»** (CLI: `--actions`). Перед операцией выбирается тенант, затем тип действия и объект применения.

### Меню операций

| № | Операция |
|---|----------|
| 1 | Замена действия «Записывать событие в базу данных» (Log to DB) |
| 2 | Замена действия «Отправлять свой ответ» (Custom Response) |
| 3 | Добавить действие «Отправить событие по протоколу Syslog» (send_to_syslog) |
| 4 | Заменить действие send_to_syslog на другое |
| 5 | **(Экспериментально)** Добавить любое действие ко всем правилам |
| 6 | **(Экспериментально)** Заменить любое действие на любое |
| 7 | **(Экспериментально)** Удалить любое действие из всех правил |

### Объект применения

После выбора действия указывается, куда применить изменения:

1. **Шаблон политики** — правила пользовательского шаблона (`config/policies/templates/user/{id}/rules`).
2. **Политика веб-приложения** — системные и пользовательские правила политики приложения.

### Замена действий (п. 6) — область применения

Для экспериментальной замены «любое на любое» доступен выбор области:

1. **Применить ко всем правилам** — обход всех правил выбранного шаблона или политики.
2. **Применить по фильтру** — фильтр по уровню критичности правила (`event.threat`: `none`, `low`, `medium`, `high`). Список уровней и количество правил формируется из ответа API.

Перед выполнением запрашивается подтверждение с указанием исходного и целевого действия, объекта и (при фильтре) уровня `threat`.

### Особенности работы с политикой веб-приложения

В политике системные и пользовательские правила обновляются **разными API**:

| Тип правила | Чтение | Обновление действий |
|-------------|--------|---------------------|
| Системное | `GET .../policies/{id}/rules/{rule_id}` | `PATCH .../policies/{id}/rules/{rule_id}` с телом `{"actions": ["uuid", ...]}` |
| Пользовательское | `GET .../policies/{id}/user_rules/{rule_id}` | `PATCH .../policies/{id}/user_rules/{rule_id}` с телом `{"configuration": {"actions": [...], "parameters": [...]}}` |

Для **системных** правил политики, у которых нет собственного оверрайда действий (`has_overrides: false`), утилита берёт действия из связанного шаблона (`policy_template_id`, `policy_template_type`) и записывает результат как оверрайд на уровне политики.

Для **пользовательских** правил действия читаются и записываются в `configuration.actions`; существующие `parameters` сохраняются.

## Настройки NGINX access.log

Пункт **«3. Управление настройками traffic_settings»** → **«4. ptaf-nginx: Настройки access.log»**.

Перед изменением настроек traffic_settings создаётся бекап в каталог `traffic_settings/{tenant_id}/`.

### Что настраивается

- Включение/выключение access log (`core_nginx_access_log`).
- Формат строки лога (`core_nginx_access_log_format`).

### Форматы лога

Список форматов загружается из файла `config/nginx_access_log_formats.yaml`. При старте меню отображаются все записи из секции `formats`; последний пункт «Пользовательский формат» позволяет ввести строку вручную.

Пример добавления нового формата:

```yaml
formats:
  - name: Мой формат
    format: '$remote_addr [$time_local] "$request" $status'
```

Для ручного ввода в меню:

```yaml
  - name: Пользовательский формат
    custom: true
```

В репозитории уже есть предустановленные форматы: Combined, Extended, Minimal, **for vector + OpenSearch** (JSON-подобная строка для Vector и OpenSearch).

Если файл не найден или повреждён, используются встроенные форматы по умолчанию.

### Другие пункты traffic_settings

| № | Настройка |
|---|-----------|
| 1 | NGINX: лимит размера запроса (`client_max_body_size`) |
| 2 | Envoy: Sticky Session |
| 3 | Envoy: TLS (мин./макс. версия) |
| 4 | NGINX: access.log |
| 5 | NGINX: error.log |
| 6 | Лимит количества приложений |
| 7 | Debug-режим (уровни логов NGINX, Envoy, PTAF) |
| 8 | Просмотр текущих настроек |

## Конфигурация

Создайте или измените конфигурационный файл `ptaf_api_client_config.json` (по умолчанию ищется в каталоге скрипта):

```json
{
  "ptaf_url": "https://your-ptaf-server",
  "username": "login",
  "password": "password",
  "api_path": "/api/ptaf/v4",
  "verify_ssl": false,
  "ssl_cert_path": null
}
```

- `ptaf_url` — базовый URL сервера PTAF PRO  
- `username` / `password` — учётные данные для получения JWT  
- `api_path` — путь к API (обычно `/api/ptaf/v4`)  
- `verify_ssl` — проверять ли SSL-сертификат  
- `ssl_cert_path` — путь к сертификату (если нужен)

## Использование

### Интерактивный режим (по умолчанию)

```bash
python3 ptaf_api_client.py
```

После входа отображается главное меню. Для части операций потребуется выбрать тенант. Версия PTAF запрашивается при старте и влияет на доступные пункты меню.

### Режим CLI (опции)

```bash
python3 ptaf_api_client.py [опции]
```

| Опция | Описание |
|-------|----------|
| `--config FILE` | Путь к конфигурационному файлу (по умолчанию `ptaf_api_client_config.json`) |
| `--debug` | Включить отладочный режим (полные запросы/ответы) |
| `--source DIR` | Импорт правил из указанной директории |
| `--export` | Экспорт правил (с запросом сохранения связей с действиями и состояния) |
| `--delete-all` | Удалить все пользовательские правила (с подтверждением) |
| `--snapshot` | Создать снапшоты конфигурации по всем доступным тенантам |
| `--policy-template` | Управление шаблонами политик |
| `--traffic-settings` | Управление traffic_settings |
| `--actions` | Управление действиями в правилах |
| `--restore` | Восстановление конфигурации из снапшота |
| `--transfer` | Копирование объектов между тенантами |
| `--tenants` | Работа с тенантами |
| `--global-lists` | Управление глобальными списками (PTAF 4.2.2+) |
| `--rules` | Работа с правилами |
| `--dangerous` | Опасные действия |

При использовании опций выполняется соответствующее действие без вывода главного меню (при необходимости запрашивается тенант или путь).

## Ограничения и известные проблемы

- **Замена действий в политике** — для системных правил без оверрайда действия наследуются из шаблона; утилита вычисляет эффективный список действий перед заменой. Экспериментальные массовые операции рекомендуется предварительно проверять на тестовом тенанте.
- **Экспорт/импорт правил с динамическими списками** — могут работать не во всех сценариях.
- **Перенос шаблона политики** — при наличии изменённых правил с системными динамическими списками возможны ошибки; маппинг глобальных списков выполняется по имени и типу (включая системные списки).
- Поведение API может отличаться в зависимости от версии PTAF и типа тенанта (agent/worker); часть функций помечена как экспериментальная.
