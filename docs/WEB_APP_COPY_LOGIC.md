# 4. Копирование веб приложения в другой тенант (Экспериментальное)

Описание полной логики пункта меню «Копирование объектов между тенантами» → «4. Копирование веб приложения в другой тенант».

---

## Общая схема

Копируется **одно** веб‑приложение из **исходного** тенанта в **целевой**: создаётся или обновляется приложение с тем же именем, подставляется шаблон политики по имени, переносятся переназначения системных и пользовательских правил политики по именам. В конце можно запустить копирование ещё одного приложения без выхода из пункта меню.

---

## Шаги по порядку

### 1. Выбор исходного тенанта

- Список тенантов: `GET auth/account/tenants` (или из кэша).
- Пользователь вводит номер (или `q` для выхода).
- Запоминаются `source_tenant_id`, `source_tenant_name`.

### 2. Переключение на исходный тенант

- Устанавливается `auth_manager.tenant_id = source_tenant_id`.
- Вызывается `update_jwt_with_tenant()` для получения tenant-level JWT.
- При ошибке — сообщение и выход, контекст восстанавливается.

### 2.1. Данные приложения и переназначения из снапшота (всегда)

- Вызов **GET /api/ptaf/v4/config/snapshot** для исходного тенанта (`get_tenant_snapshot(source_tenant_id)`). При ошибке — выход.
- Парсинг снапшота (`snapshot_parser`): список приложений, для выбранного — имя, hosts, locations, protection_mode, имя шаблона, `system_rule_overrides`, `user_rules`.
- Пользователь выбирает приложение из списка приложений снапшота. При отмене — выход.
- Заполняются: `app_name`, `hosts`, `locations`, `protection_mode`, `source_template_name`, `source_rule_details_by_name` (только оверрайды системных правил), `source_user_rule_details_by_name` (из `user_rules` снапшота).
- По имени шаблона в исходном тенанте ищется шаблон (GET user templates) → `source_template_id`. Если не найден — выход с сообщением.

### 4. Экспорт шаблона (на случай, если в целевом тенанте его нет)

- В исходном тенанте вызывается `PolicyTemplateManager.export_template(source_template_id, temp_dir, include_user_rules=True)`.
- Результат сохраняется во временный файл `template_export_file`.
- Если экспорт не удался — `template_export_file = None`; при отсутствии шаблона в целевом тенанте будет использован fallback с переключением на исходный тенант.

### 5. (Пропуск шага 5 в коде — нумерация из описания.)

### 6. Выбор целевого тенанта

- Снова список тенантов, выбор по номеру.
- Проверка: исходный и целевой не должны совпадать.

### 7. Переключение на целевой тенант

- `auth_manager.tenant_id = target_tenant_id`, обновление JWT.
- **GET** пользовательских шаблонов в целевом тенанте.
- По имени `source_template_name` ищется шаблон → `target_template_id`.

**Если шаблон с таким именем не найден:**

- Сообщение, что шаблон не найден, попытка автоматически скопировать его.
- Если есть `template_export_file`: вызывается `copy_template_to_another_tenant(..., export_file=template_export_file)` (импорт в целевой тенант без переключения на исходный).
- Иначе: переключение на исходный тенант → `copy_template_to_another_tenant(...)` без `export_file` (экспорт + импорт) → переключение обратно на целевой.
- После копирования — повторный **GET** пользовательских шаблонов и поиск `target_template_id` по имени.
- Временный файл экспорта шаблона удаляется.

### 7.2. Создание или обновление приложения в целевом тенанте

Формируется тело запроса `app_payload`: name, policy_template_id (целевой), traffic_profiles, proxy_ssl_verify, enable_websockets, protection_mode, hosts, locations, load_balancer, ssl_options_reloaded.

- **GET config/applications** в целевом тенанте.
- Если есть приложение с именем `app_name`:
  - Сразу выполняется **PATCH config/applications/{id}** с `app_payload` (name, policy_template_id, hosts, locations, protection_mode и т.д.); из ответа или существующего объекта берётся `created_app` и `policy_id`. Вопрос пользователю не задаётся — по умолчанию обновление (суть переноса).
- Если приложения с таким именем нет:
  - **POST config/applications** с `app_payload`.
  - При 200/201 — `created_app` из ответа.
  - При 422 и `errors.name` = `must_be_unique`: поиск приложения по имени в целевом тенанте, затем **PATCH** по найденному `id` с тем же телом; формирование `created_app`.
  - При любой другой ошибке — вывод ошибки (в т.ч. метод, URI, тело запроса/ответа), восстановление контекста и выход.

Из `created_app` берётся `target_policy_id` (policy_id созданной/обновленной политики приложения).

### 8. Перенос системных правил политики

- **GET** системных правил политики `target_policy_id` в целевом тенанте.
- Для каждого целевого системного правила по **имени** ищется запись в `source_rule_details_by_name`.
- Если найдено: сравниваются `enabled` и `actions` с целевым (GET деталей правила в целевой политике). При отличии — **PATCH** системного правила в целевой политике (enabled, actions).
- Подсчёт: обновлено / пропущено / ошибок.

### 9. Перенос пользовательских правил политики

- **GET** пользовательских правил политики `target_policy_id` в целевом тенанте.
- Для каждого целевого пользовательского правила по **имени** ищется запись в `source_user_rule_details_by_name`.
- Если найдено: сравниваются `enabled` и `actions` с целевым (GET деталей пользовательского правила). При отличии — **PATCH** пользовательского правила в политике (enabled, actions).
- Подсчёт: обновлено / пропущено / ошибок.

### 10. Завершение и повтор

- Вывод итога: системные и пользовательские правила — сколько обновлено, пропущено, ошибок.
- Восстановление контекста тенанта: `auth_manager.tenant_id = original_tenant_id`, при необходимости `update_jwt_with_tenant()`.
- Вопрос: **«Скопировать ещё одно веб приложение в другой тенант? (y/n)»**.
- При **y** — повторный вызов `run_copy_web_app_flow(api_client, snapshot_manager)` (снова с выбора исходного тенанта и т.д.).
- При **n** — возврат в меню «Копирование объектов между тенантами».

---

## Что переносится

| Объект | Как |
|--------|-----|
| Приложение | Создание (POST) или обновление (PATCH): name, policy_template_id, hosts, locations, protection_mode, traffic_profiles, proxy_ssl_verify, enable_websockets, load_balancer. |
| Шаблон политики | Не создаётся заново; используется существующий в целевом тенанте по **имени**. Если шаблона с таким именем нет — он копируется из исходного (экспорт/импорт или импорт из заранее экспортированного файла). |
| Системные правила политики | Только переназначения: **enabled** и **actions** по совпадению **имени** правила. Правила в целевой политике не создаются, только обновляются. |
| Пользовательские правила политики | Аналогично: **enabled** и **actions** по совпадению **имени** правила в политике приложения. |

Связанные действия и глобальные списки в рамках этого сценария не копируются; маппинг action ID между тенантами не выполняется (подразумевается, что в целевом тенанте уже есть нужные действия/списки или они совпадают по ID).

---

## Источники данных для правил

- **Из снапшота (2.1):** системные оверрайды и пользовательские правила берутся из структуры снапшота (applications → policies → user_templates; парсер извлекает только переназначения и user_rules).
- **Из API (классический путь):** системные и пользовательские правила и их детали запрашиваются по `source_policy_id` в исходном тенанте перед переключением на целевой.

---

## Ошибки и отмена

- На любом шаге при ошибке API или отмене пользователем (например, `q` при выборе тенанта/приложения) контекст тенанта восстанавливается (`original_tenant_id`), при необходимости обновляется JWT, выполнение выхода из потока.
- При ошибках создания/обновления приложения или правил выводится HTTP-код, метод, URI, тело запроса и ответа (функция `_print_http_error`).

---

## Файлы и зависимости

- **web_app_copy.py**: `run_copy_web_app_flow(api_client, snapshot_manager)` — основной поток.
- **snapshot_parser.py**: разбор снапшота (приложения, шаблон по политике, system_rule_overrides, user_rules).
- **policy_template_manager.py**: экспорт шаблона, `copy_template_to_another_tenant` (с опцией `export_file`).
- **api_client**: get_applications, create_application, update_application, get_user_templates, get_policy_system_rules, get_policy_system_rule_details, update_policy_system_rule, get_policy_user_rules, get_policy_user_rule_details, update_policy_user_rule, get_template_details и др.

Вызов из меню: **snapshot_manager.manage_tenant_transfer()** → пункт 4 → **run_copy_web_app_flow(api_client, snapshot_manager)**.
